# Device-read tooling for a registered worker

## Description

Adds CAP-7: `scripts/device-preview.mjs [session-fixture] [--history <history-fixture>] [--no-build]` (F9). Both the positional and the `--history` value are names under `fixtures/` without `.json` (the script appends it); the doc's commands use that form (e.g. `session-gave-up`, `--history history-invalid-null`).

- **Script.** It exports pure helpers that `main()` only wires: `parseArgs(argv)` → `{ session, history, build }` (`--history` consumes its value; a usage error is thrown, rule 6, on `--history` with no value or a `--`-prefixed value, a repeated `--history`, a second positional, an unknown flag, a positional not starting `session-` or a `--history` value not starting `history-`); `seedPage({ sessionJson?, historyJson? })` (no string overload; `seedPage({})` throws, rule 6) stores `wordcell:session` and/or `wordcell:history`, nothing for an absent one, and throws on a non-JSON one; an absent fixture is `undefined`, never a falsy parsed value (`history-invalid-null` parses to `null` and is stored); `hintLines(url, parsed)` takes `parseArgs`' result, derives seeded (session or history given) itself and returns the printed lines. `main()` runs in this order: `parseArgs` → read and JSON-parse the fixtures → (no fixture) remove a stale `dist/seed.html` → Tailscale lookup → build → seed-page write (either fixture given) → preview → serve. The seed page's unregister code and the existing test's `unregister()` assertion stay; its comment and the doc call it a guard for an uncontrolled first visit (other comments, e.g. the usage line, follow the new CLI).
- **Printed lines.** The phone URL line is `On the phone (Tailscale connected): <url>/seed.html` whenever a seed page is written (session or `--history` fixture), else `<url>/`. A seed run then prints "Seed or re-seed: clear this origin's site data on the phone first.", replacing today's line 106 ("After a new build, …", which contradicts CAP-7); a no-fixture run prints instead "Fresh install: clear site data first." and "Update read (G3): keep site data."; "Ctrl+C stops." stays in both variants. `hintLines` returns one element per line, no blank entries: the URL line, the hint line(s), then "Ctrl+C stops." last; `main()` adds the surrounding blank lines. Tests assert the exact lines.
- **Seed steps** (`docs/device-testing.md`, G4–G6, A-A11; replace "Repeat step 3"): first, with every WordCell window closed (swipe the app from recents, close the origin's Chrome tabs; a resumed renderer's AD-9 hide flush would write its game over the seeded `wordcell:session`), clear the origin's site data (before every seed, re-seed or fresh-install read; Chrome ⋮ → Settings → Site settings → All sites → the tailnet origin → Delete data or Clear & reset (unverified), replacing step 2's address-bar path, which needs an open origin tab), then seed; if the app is not installed, install it from the tab the seed page opened (Chrome's own install UI, G1); close the Chrome tab promptly without playing (the seed page's `location.replace('/')` boots the game there, and closing it runs the AD-9 hide flush) and launch the installed app cold. Doc defaults: G4 `session-place-free-letter-redo-tail` and `session-gave-up` (the other G4 boundaries by play), G5 `session-won-words`, G6 `--history history-invalid-null` (history-only seed).
- **Desktop rows (G20–G22).** One line: open the tailnet URL (or `localhost:4173`) in desktop Chrome, clear its site data before reading a new build, confirm the menu footer before recording the row.
- **Update read** (`device-checks.md` G3's order, with A's and B's readiness steps; wherever a window shows the Q-38 message, Reload, then read the menu footer). A: `WORDCELL_APP_VERSION=A node scripts/device-preview.mjs` (the "Fresh install" line); with every window closed, clear site data as the Seed steps say; then if the app is installed launch it online, otherwise open `<url>/` in Chrome, install (G1), close the tab and launch; A's readiness step, Ctrl+C (stops A's server), then `WORDCELL_APP_VERSION=B node scripts/device-preview.mjs` (no fixture, keeping site data only from A to B, the "Update read (G3): keep site data." line); the script's `npm run build` inherits the env (`scripts/app-version.mjs`), so the footer shows which build runs (`A`/`B` carry no commit: the doc records `git rev-parse --short HEAD` next to them), and both runs build (no `--no-build`), as does the first run after an update read, so the footer carries the SHA again; no new CLI flag. A spoiled read is redone once from the start (A's command and fresh install, G3); a second consecutive one routes as G3 says. The doc's G3 section also states the production variant (CAP-10, release-checklist step 4): A is the installed production build, its readiness step release-checklist step 2's G2 readiness on it, before step 3's push; B the 1.0.0 deploy, no `device-preview` run; spoiled reads route as step 4 says.
- **Also in the doc:** the offline readiness step and launch (G2), and uninstalling the tailnet-origin app before entry 12's production install.
- **Nothing new ships in `dist/` deploys (F9):** the change touches only `scripts/device-preview.mjs`, `scripts/device-preview.test.mjs` and `docs/device-testing.md` (no `src/`, `public/` or `vite.config.ts` change, so the generated worker's policy and `sw.js` config are unchanged).
- **Interface:** `device-preview.mjs` CLI (`--history`), the doc's G2/G3/G4–G6/Desktop procedures. **Tests:** Device-preview seed and hint cases (`scripts/device-preview.test.mjs`). **Owns:** The device-read tooling and procedure. **Consumers:** Entry 11 (tailnet and desktop reads), entry 12 (production install and update read).

## Acceptance Criteria

Verify: `scripts/device-preview.test.mjs` passes new `AD-17` cases: `parseArgs`: each listed usage error throws (including a `history-` positional); `--no-build` in any position gives `build: false`; a session positional alone gives no history; history-only (`--history history-x`: no session); session plus history in either order; `seedPage` history-only with `fixtures/history-invalid-null.json` (stores `wordcell:history` as `"null"`, no `wordcell:session`), session plus history (sets both), a non-JSON `historyJson` (`''`: an empty file is not absent) throwing; `hintLines` exact lines of both variants, `hintLines(url, parseArgs(['--history', 'history-x']))`'s URL line ending `/seed.html` and `hintLines(url, parseArgs([]))`'s ending `/`; the existing cases are ported to `seedPage({ sessionJson })` and keep their assertions (session stored, `unregister()`, `location.replace('/')`, non-JSON throws); `docs/device-testing.md` covers each step CAP-7 lists (checked against `device-checks.md` G2–G6 and G20–G22); the plan records: a stub `dist/seed.html` is gone after `npm run build` (Vite empties `dist/`); a no-fixture `--no-build` run removes a stub `dist/seed.html` and does not fail when none exists; a missing fixture name fails before `npm run build` starts (both run as `timeout -s INT 60 node scripts/device-preview.mjs --no-build`, the missing name added for the second; SIGINT runs `stop()`; then `tailscale serve status` shows no share); `WORDCELL_APP_VERSION=A npm run build` then a grep of `dist/assets/*.js` finds the footer string `A` (`` textContent=`A` ``) and a `WORDCELL_APP_VERSION=B` build gives a different `dist/sw.js` (both hashes recorded), followed by a normal rebuild; outside `_bmad-output/`, the diff touches only the three files above; `npm run test:all` is green.
