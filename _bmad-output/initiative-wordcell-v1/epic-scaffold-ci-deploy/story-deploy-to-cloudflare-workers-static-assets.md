# Deploy to Cloudflare Workers static assets

## Description

First confirms origin and the CLOUDFLARE_API_TOKEN and CLOUDFLARE_ACCOUNT_ID secrets and halts if origin is wrong or either secret is missing, then adds wrangler pinned at exactly 4.141.0, wrangler.jsonc, public/_headers, public/.assetsignore and deploy.yml, which deploys the `dist` artifact of ticket 1.8's ci.yml run unrebuilt after a green push to main.

## Acceptance Criteria

Verify: every proof in the Delta checks > Local bullet below (the single list of local proofs), plus `docker run --rm -v "$PWD":/repo -w /repo rhysd/actionlint:1.7.12` exits 0 with empty output on the tree including `deploy.yml`; after the owner merges and pushes to main, the live site returns the AD-18 cache headers and 404s (gate 4).

**Build precondition:** clean tree on `epic-1-scaffold`. The build runs unattended; `hitl: true` refers only to the owner's gate-4 dashboard checks, merge and push.

**First step:** `git remote get-url origin` is exactly one of `git@github.com:jmb496/wordcell.git`, `git@github.com:jmb496/wordcell`, `ssh://git@github.com/jmb496/wordcell.git`, `ssh://git@github.com/jmb496/wordcell`, `https://github.com/jmb496/wordcell.git`, `https://github.com/jmb496/wordcell`, and `gh secret list` shows `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` (both present, re-confirmed 2026-09-28). Halt if either secret is missing, or if origin is none of these (this ticket's tightening of SPEC CAP-9's "halts only if one is missing", backed by AD-18's "a GitHub remote" prerequisite; the plan lists it with the SPEC CAP-9 errata for the D8 audit / retrospective).

**Delta checks (delta-checks.md rows for CAP 9):**

- `wrangler` devDependency: `npm install --save-dev --save-exact wrangler@4.141.0`; `package.json` pins `4.141.0` exactly and `package-lock.json` is updated with it.
- `deploy.yml`, `wrangler.jsonc`, `_headers`, `.assetsignore`: SPEC CAP-9 success. `wrangler.jsonc` has `name: "wordcell"`, a pinned `compatibility_date` (the build date as a literal `YYYY-MM-DD`, 2026-09-28 if built today, verified accepted by wrangler 4.141.0 without warning; if 4.141.0 warns about the build date, use the latest date it accepts without warning; the plan records the date chosen), `workers_dev: true`, `preview_urls: false` (disables wrangler 4's per-version preview URLs, per A-A6 "no preview deploys" and SPEC's "no preview environment"; a recorded technical addition beyond the build-notes key list, the plan quotes it), `assets: { directory: "./dist" }`, no `main`, no `not_found_handling`, `html_handling` left at its default: exactly the keys `name`, `compatibility_date`, `workers_dev`, `preview_urls`, `assets` (only `assets.directory`), no others (no `$schema`). `public/_headers` per AD-18; `public/.assetsignore` lists `.vite`; both are in `dist/` after `npm run build`. `deploy.yml`:
  - Top-level `name: Deploy`. Trigger: `on: workflow_run` with `workflows: [CI]` (ci.yml's `name:`, not its file name; renaming it breaks deploy), `types: [completed]`, `branches: [main]`. Workflow-level (where `ci.yml` places it) `permissions: actions: read, contents: read` per build-notes CAP-9 (`actions: read` for the cross-run download). One job `deploy` on `ubuntu-latest`, `timeout-minutes: 20` (see Post-deploy check), carrying the `if:` (`conclusion == 'success'`, `event == 'push'`, `head_branch == 'main'`) and `concurrency: { group: deploy, cancel-in-progress: false }` [ASSUMPTION] on the job, not the workflow, so a skipped run never joins the group or replaces a pending deploy; observed at gate 4 (a skipped non-main run must not show as pending or cancel a `main` deploy; if it does, report, do not change the workflow). A new deploy.yml run uses `main`'s HEAD at trigger time (workflow_run semantics); a re-run reuses that run's workflow file and artifact; meanwhile the checkout pins config and lockfile to the CI run's `head_sha`; the owner re-runs only the latest `deploy.yml` run, since re-running an older one redeploys an older artifact (a silent rollback). Re-running a `deploy.yml` run redeploys that run's CI artifact and fails at download once the 7-day artifact has expired. Known side effect, not a rollback path: re-running an older CI run on `main` rebuilds and redeploys that commit and, via ci.yml's concurrency, cancels a newer in-flight `main` CI run; the owner does not do it and uses AD-18's revert or `wrangler rollback`.
  - Steps, named in `ci.yml`'s style: `checkout`, `setup-node`, `npm ci`, `download dist`, `verify dist`, `deploy`, `post-deploy check` (the wait, then checks 1–9). `checkout`: `actions/checkout@v7` with `ref: ${{ github.event.workflow_run.head_sha }}` (config and lockfile match the tested artifact) and `persist-credentials: false`; `actions/setup-node@v7` Node 24, `cache: npm`, as in `ci.yml`; `npm ci`; `actions/download-artifact@v8` (current major per `gh release view` on 2026-09-28; the plan records the check) with `name: dist`, `path: dist`, `run-id: ${{ github.event.workflow_run.id }}`, `github-token: ${{ github.token }}`; fail if `dist/index.html`, `dist/_headers`, `dist/.assetsignore`, `dist/sw.js`, `dist/manifest.webmanifest` or `dist/.vite/manifest.json` is missing (the last so the live 404 proves `.assetsignore` excluded a present file) or `dist/assets/` has no `*.js`; no rebuild; `npx --no-install wrangler deploy` (a missing local wrangler fails rather than fetching another version, rule 6) with `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` from secrets in `env:` on that step only.
  - Post-deploy check: inline bash in `deploy.yml` (no new script file, so actionlint's shellcheck covers it); `deploy` and `post-deploy check` set `shell: bash` (`-eo pipefail`, so a failed `wrangler deploy | tee` fails the step, rule 6). The deploy step runs `npx --no-install wrangler deploy 2>&1 | tee "$RUNNER_TEMP/wrangler-deploy.log"`; the check reads from that file the first URL matching `https://wordcell\.[^/ ]+\.workers\.dev` (the worker's own host), failing if none. Every curl uses `--max-time 10`. First one shared propagation wait: at most 24 attempts 5 s apart, each `curl -s --max-time 10 -o "$tmp" -w '%{http_code}' <url>/` (no `--compressed`, no `Accept-Encoding`; the `-w` output is the status, compared to 200) then `cmp -s "$tmp" dist/index.html` ([ASSUMPTION] static assets serves `index.html` byte-identical, confirmed by the first live deploy; if that deploy fails only on the body mismatch, do not loosen the check; report it as for `_headers` below); as in the checks, the curl exit code is captured without aborting the step, and a curl error, non-200 status or body mismatch fails the attempt; each failed attempt is logged (curl exit code or status, body byte length and hash, not the HTML). The wait proves the new version only when `index.html` changed (it embeds the hashed chunk names); when it is identical (re-runs, docs-only or `_headers`-only commits) the wait passes at once and the per-check attempts are the only propagation guard (known limit, no further mechanism). Then 9 checks in this order: (1) `/assets/<file>` (the first match of the bash glob `dist/assets/*.js`, logged by name) has the AD-18 immutable value; (2) `/` `no-cache`; (3) `/sw.js` `no-cache`; (4) `/manifest.webmanifest` `no-cache`; (5) `/index.html` via `curl -sIL`, final header block (after the last `HTTP/` status line) 200 and `no-cache`; (6) `/.vite/manifest.json` 404; (7) `/assets/does-not-exist.js` 404; (8) `/_headers` 404; (9) `/.assetsignore` 404. Checks 1–4 use `curl -sI` without `-L` and expect 200 on that single response; in checks 1–5 the relevant header block must contain exactly one `cache-control` line (name matched case-insensitively after stripping `\r` and surrounding whitespace) whose value equals the AD-18 value; none or several fails the attempt and all such lines are logged. [ASSUMPTION] `_headers` replaces rather than merges with the platform default `cache-control`, verified by the first live deploy; if that deploy fails only on a duplicate or merged `cache-control`, the assumption failed: do not loosen the check; report it as an AD-18/spine follow-up (the owner may roll back per AD-18). Checks 6–9 use `curl -sI` and compare the single response's status. Check 5: default `html_handling` answers `/index.html` with a 307 to `/` and never serves it directly, so check 5 repeats check 2 via the redirect and exists to log the 307: deploy.yml logs the first response's status and its `cache-control` line, or `(none)` (informational only). `/index.html` stays in `_headers` per AD-18; the plan records a SPEC CAP-9 erratum (default `html_handling` never serves `/index.html` with 200) for the D8 audit / retrospective. Each check has at most 3 attempts 5 s apart. An attempt fails on any curl error (exit code captured without aborting the step), status or header mismatch; every failed attempt is logged (URL, expected, got); the step fails non-zero at the first check (or the wait) that runs out of attempts, printing its URL, expected value and last response. Worst case: setup (checkout + `npm ci` cache hit ~1–2 min, miss ~3 min, download and `wrangler deploy` < 1 min) ≤ 4 min, wait ≤ 24 × 15 s = 6 min, checks ≤ 9 × 3 × 15 s = 6.75 min, total ≈ 17 min, inside `timeout-minutes: 20`. [ASSUMPTION] The wait and retries are bounded waits for edge propagation (e.g. a new worker's DNS/TLS on the first deploy); every mismatch still fails the job after a bounded wait, so this complies with rule 6; no ref prescribes a retry. No automatic rollback, the owner rolls back per AD-18.
