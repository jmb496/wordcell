# CI workflow

## Description

Adds .github/workflows/ci.yml: on every push and PR, two jobs. `test` (Node 24, npm ci): lint → check → unit → build (size budget) → dist-smoke → upload dist/ with hidden files as artifact dist for entry 9's deploy.yml → build:test → e2e (android, desktop, pwa). `screens` (`needs: test`): screenshot job in the container.

**Build notes fixed here:**

- Triggers: `push: { branches: ['**'] }` (all branches, no tags) and `pull_request`. Top-level `permissions: contents: read` [default]; `concurrency: { group: ci-${{ github.ref }}, cancel-in-progress: true }` [default], so of two overlapping runs on `main` the older is cancelled and cannot hand entry 9 stale bytes (entry 9 deploys only `conclusion == 'success'`, so cancelled runs never deploy); a manual re-run of an older run is not covered (see Handoff). A branch with an open PR runs twice (push ref and `refs/pull/N/merge` are different groups); intended, the PR run tests the merge result. Workflow `name: CI` [default] (entry 9's `workflow_run.workflows` matches it). Each job has `timeout-minutes: 30` [default].
- Jobs [default]: `test` on `ubuntu-latest` runs every step from lint through the e2e `pwa` step in AD-18 order; the step names are exactly these, in this order: checkout, setup-node, npm ci, playwright install, lint, check, unit, build, dist-smoke, upload dist, build:test, e2e, pwa, flaky report (`!cancelled()`), upload test-results (`failure()`); a job timeout counts as cancelled, so no report then (accepted); `screens` has `needs: test` and runs in the container. Each job does its own checkout and `npm ci`. Entry 9's `conclusion == 'success'` then covers both.
- Actions referenced by major tag (`@vN`, not SHA) [default]: `actions/checkout`, `actions/setup-node`, `actions/upload-artifact`, each at its current major at build time (check with `gh release view -R actions/<name>`), upload-artifact ≥ v4.4 for `include-hidden-files`; the plan records the majors, and entry 9's `download-artifact` uses the matching major. Every `actions/checkout` uses the default path (no `path:` input): `/home/runner/work/wordcell/wordcell` and `/__w/wordcell/wordcell`, neither with a `pwa` segment (1.3 plan handoff: `testIgnore` `'**/pwa/**'` matches absolute paths).
- `test` setup: `actions/setup-node` with `node-version: 24` and `cache: npm`, `npm ci`, then `npx playwright install --with-deps chromium` before the first Playwright step (dist-smoke).
- The upload uses `actions/upload-artifact` under the fixed name `dist` with `path: dist/`, `include-hidden-files: true`, `if-no-files-found: error` (AGENTS.md rule 6), `retention-days: 7` [default] (entry 9 downloads at `workflow_run` time) and `overwrite: true` (a "Re-run jobs" attempt would otherwise fail on the existing name, and entry 9 gets the bytes of the attempt that went green), so the artifact is the exact `dist/` CI tested, `.vite/` included (and `.assetsignore` once entry 9 adds it; entry 9's `.assetsignore` then excludes `.vite` at deploy).
- After `build:test`, the `pwa` step runs `npx playwright test -c playwright.pwa.config.ts --project pwa` with `env: PW_PREVIEW: dist-test`, so `dist-test/` is built once, from `build:test` (instead of AD-17 Scripts' `test:e2e:pwa`, per the epic Notes owner decision 2026-09-27: CI runs the Playwright `pwa` project directly after `build:test`, building `dist-test/` once).
- Flaky report (1.3 plan handoff: CI `retries: 2` in `playwright.config.ts` and `playwright.pwa.config.ts` can hide flaky failures) [default]:
  - The three Playwright steps in `test`, each with a step `id` and its own `PLAYWRIGHT_JSON_OUTPUT_NAME: ${{ runner.temp }}/pw-json/<id>.json` (never under `test-results/`, which Playwright empties each run, `dist/` or `dist-test/`): `dist-smoke` runs `npm run test:e2e:dist -- --reporter=github,json`; `e2e` runs `npm run test:e2e -- --reporter=github,json` (android and desktop in one step); `pwa` runs `npx playwright test -c playwright.pwa.config.ts --project pwa --reporter=github,json`.
  - The report step runs `if: ${{ !cancelled() }}` with `shell: bash` (`bash --noprofile --norc -eo pipefail {0}`) and parses inline with `jq` (preinstalled on `ubuntu-latest`; no new file under `scripts/`). It receives everything through step `env:` (`OUTCOME_DIST_SMOKE: ${{ steps.dist-smoke.outcome }}`, `OUTCOME_E2E`, `OUTCOME_PWA` likewise, `PW_JSON_DIR: ${{ runner.temp }}/pw-json`); its `run:` body contains no `${{ }}`, so Verify step 7 runs it unchanged. It reads a step's JSON when that step's outcome is `success`, or `failure` with the file present; the filter walks suites recursively carrying the describe-title path, starting below each root file suite (its title is the file, so it is not repeated), e.g. `def specs_with_path($p): (.specs[]? | {p: $p, s: .}), (.suites[]? | specs_with_path($p + [.title])); .suites[] | specs_with_path([])`. The filter lives in one single-quoted assignment (`filter='…'`), the line before that assignment is `# shellcheck disable=SC2016` [default] (the single-quoted filter's `$p` would otherwise trip actionlint's shellcheck), and every `jq` call uses `"$filter"` (or `-e "$filter"`); no actionlint flag or config change; the plan quotes the directive.
  - Summary in `$GITHUB_STEP_SUMMARY`: the heading `## Flaky tests`; then, as markdown `- ` list items, one `<id>: not run` line per step whose outcome is `skipped` (specified outcome) and one `<id>: failed before reporting` line per step with outcome `failure` and no JSON file (the job already fails on that step), in step order dist-smoke, e2e, pwa; then either one `- ` item per `specs[].tests[]` entry with `status == "flaky"` (i.e. per spec × project) across all read reports, in step order (dist-smoke, e2e, pwa), then the filter's emission order (a suite's own specs first, then its child suites, depth-first, and within a spec, `tests[]` order as written in the JSON), its text `[projectName, spec.file] + describePath + [spec.title]` joined with ` > ` (`projectName` = `tests[].projectName`, `spec.file` = the spec's `file` field as written in the JSON; a file-level test has no describe segment, never an empty one), then CR and LF replaced by a space (one pipeline; this text serves both the summary item and the warning), in a double-backtick code span with padding spaces (``` `` text `` ```, so single backticks in titles survive) [default], or the single item `No flaky tests.`, written also when no report was read (the not-run lines say why) [default]. The step validates all three inputs (outcome value, file presence, parse) before writing anything, and builds the whole summary and the warnings into a variable or temp file, appending to `$GITHUB_STEP_SUMMARY` and printing the warnings only after every `jq` call succeeded (so JSON that parses but has an unexpected shape, e.g. `{}`, also leaves nothing written); on any `exit 1` the summary file stays empty: an `OUTCOME_*` value other than `success`, `failure`, `skipped`, a step with outcome `success` whose JSON is missing, any JSON the step reads and cannot parse whatever the outcome, and any JSON that parses but has an unexpected shape (handled like a parse error, never left to jq's own message, e.g. "Cannot iterate over null", which names no step) [default], each fail the report step with an explicit `exit 1` and a message on stderr (`>&2`) naming the step id (a bug, not a flaky finding, AGENTS.md rule 6). It emits one `::warning::Flaky: <text>` per flaky entry, in the same order, `<text>` being exactly the summary item's text without the code span (describe titles included), with `%` escaped as `%25` (CR/LF can no longer occur). Flaky tests never fail the job (report, not gate).
  - The report is a signal only: names, no traces (a test that passed on retry keeps no trace, since failure artifacts upload only `if: failure()`).
- `screens`: `container: { image: mcr.microsoft.com/playwright:v1.63.0-noble, options: --init --ipc=host }` (mirrors `package.json` `test:screens`), job-level `env: WORDCELL_SCREENS_CONTAINER: '1'`; steps checkout, npm ci, test:screens:run, upload `test-results-screens` (`if: failure()`). It uses the image's bundled Node (recorded; must satisfy `engines` ≥ 22.12; the plan records `docker run --rm mcr.microsoft.com/playwright:v1.63.0-noble node --version`, compares it with 22.12 and halts the ticket if lower) (no setup-node) and no `playwright install` (the image ships browsers) [default].
