# Dictionary load, retry and Validate

## Description

- Interface: dictionary.svelte.ts exports `dictionary` { state, words, load(), retry() } (keeps `dictionaryUrl`; load() and retry() return Promise<void>, resolving once state leaves 'loading', never rejecting for AD-8 outcomes; any other rejection reaches the AD-15 handler); test hook gains dictionaryState(); primary-action gains the Validate path; banner component.
- Tests: R-38 shell load and Validate enablement; R-73 Validate saved; §2 replay never consults the dictionary (restore to Place with the route failing); Q-42 404 → reload; AD-8 shell Vitest (never-closing body → failed after 30 s fake time); AD-16 halted boot requests no dictionary (Playwright).
- Owns: The dictionary state, the banner and the Validate label rules.
- Store: `dictionary` is one object with a reactive `state` getter (`'loading' | 'ready' | 'failed'`, initially 'loading' before load() starts) and a `words` getter; `words` is assigned before `state` becomes 'ready'. game.svelte.ts passes `dictionary.state === 'ready' ? dictionary.words : undefined` as ctx.dictionary (build-notes CAP-8), replacing today's `import { words }`. The feedback shell Vitest's `vi.doMock` of dictionary.svelte.ts (ticket 3.4) exports a ready state with its inline Set. `retry()` throws unless state is 'failed' and, except on the reload branch, sets state 'loading' synchronously before its fetch, so the banner unmounts before another tap; `load()` throws if called twice (AGENTS.md rule 6).
- Load: load() and each retry() get a new AbortController and a 30 s timeout covering fetch plus response.text(); the timeout is a `setTimeout` calling `controller.abort()`, cleared on settle like main.ts fontCheck's timer, never `AbortSignal.timeout` (fake clocks miss it). text() races the abort signal so a stalled body fails at 30 s whatever the stream does (SPEC.review-log.md Pass 3 open major 8); the losing promise gets a no-op catch, so a timeout ends `failed`, never AD-15 fatal. A non-OK response, fetch or text() rejecting, the abort and an empty list (after the LF split with empty lines dropped) all give `failed` (AD-8); only a 404, at any fetch, sets the (unexported) reload-on-next-retry flag. retry() refetches in place; with the flag set the next Reload calls location.reload() (no fetch; state stays 'failed'; resolves at once), except under a controlling service worker (`navigator.serviceWorker?.controller`), where it never calls location.reload() and the banner stays until the next launch (Q-42); what else Reload does there is open (Notes).
- Start: main.ts schedules load() only on the path that mounts App (active or Session-rejected root), never on the standalone halted path (main.ts returns before registerLifecycle there, and whenVisible() would throw). After a double requestAnimationFrame following the mount it checks `game.state.kind !== 'halted'` before `await game.whenVisible()` and again immediately before load(), since a halt can arrive while waiting (AD-16). A load already in flight when a halt occurs just settles (state only; the halted surface replaces the board).
- Validate: enabled iff `view.canValidate` and state 'ready'; one tap runs the engine's Validate once (EXPERIENCE.md; dispatch is synchronous, so no extra guard). Labels follow EXPERIENCE.md Component Patterns › Validate precedence: `Word list unavailable` > `Loading words…` > `Need 3+ letters` (today App.svelte checks `Need 3+ letters` first). In Idle it is disabled, labelled `Loading words…` / `Word list unavailable` while loading/failed, else plain `Validate`. Per DESIGN.md Ink, every disabled-reason label (`Word list unavailable`, `Loading words…`, `Need 3+ letters`) uses the reason style (ink secondary) in Composing and Idle; plain Idle `Validate` stays ink disabled (today App.svelte sets reason only for `Need 3+ letters`).
- Text: src/ui/text.ts gains `Loading words…`, `Word list unavailable`, `Word list didn't load.` and `invalidWord(word)`, rendering `<WORD> isn't in the word list.`; it takes the engine spelling (`game.feedback.rejectedWord`) and uppercases it itself (`QU` as `QU`; src/ui/text.test.ts case `invalidWord('tan')` → `TAN isn't in the word list.`; EXPERIENCE.md catalogue, AGENTS.md; deferred here by the ticket 3.4 plan).
- Invalid-word line: DESIGN.md look (✕, error colour; the ✕ sits in its own aria-hidden element); on the minimal board it sits in a line near the primary action while `rejectedWord` is set; its polite live-region announcement (EXPERIENCE.md Accessibility) is deferred to epic 5 (tray UI).
- Banner: src/ui/DictionaryBanner.svelte, rendered on the active board while `dictionary.state === 'failed'`, directly after the App.svelte top row with the DESIGN.md Dictionary-failed banner colours, type and secondary `Reload` (the 44 px sticky offset comes with the epic-4 top bar): `Word list didn't load.` with a `Reload` button calling `dictionary.retry()`. Board only, not on the Session-rejected root; rendered straight from state, no AD-11 gesture latch until epic 4.
- Continuity: the interim primary-action LABELS table and label assertions in e2e/game-store.spec.ts (marked 'Interim … entry 9') are rewritten against a routed dictionary state, keeping session-idle-pending-draft.json with its ready-state expectation (disabled plain `Validate`); other specs asserting a plain `Validate` label (history.spec.ts, nav.spec.ts, lifecycle.spec.ts, etc.) wait for dictionaryState() 'ready' first; in paused-clock specs (lifecycle.spec.ts) that wait follows a runFor (so the double rAF fires) and uses expect.poll, not a rAF-polled waitForFunction; e2e/blocking.spec.ts "healthy boot stays active past the 30 s font timeout" waits for 'ready' before its runFor(31_000), which now also fires the dictionary timeout. `dictionaryState()` is added to src/shell/test-hook.ts and e2e/globals.d.ts; e2e/test-hook.spec.ts and e2e/pwa/test-hook.spec.ts expect keys ['current','dictionaryState','loaded']. e2e/placeholder.screens.spec.ts waits for dictionaryState() 'ready' before capture (regenerate the baseline with `npm run test:screens` only if the image changes).

## Acceptance Criteria

- Verify: npm run test:all is green.
- Playwright android, route **/en*.txt; the Retry, Timeout and banner cases are named with AD-8.
- R-38: with the route held, session-composing.json shows a disabled `Loading words…` and dictionaryState() 'loading' before fulfilment, then Validate enabled and TAN → Place after 'ready' (rule-coverage R-38 row). session-composing-draft-2-letters.json shows `Loading words…` while held and `Word list unavailable` when failing (precedence over `Need 3+ letters`). session-idle-fresh.json shows `Loading words…`, `Word list unavailable`, and plain `Validate` once ready. Reason-label cases assert the ink-secondary colour as the existing 2-letter case does.
- Invalid word: a non-empty word list without tan → the message element has exact text `TAN isn't in the word list.`, the phase stays Composing, and the stored Session's moves and cursor are unchanged and it equals current().session (only activeMs may grow; R-38); the next changing dispatch (Undo) clears it.
- R-73: in the existing session-place.json per-dispatch test (name gains Validate), wait for dictionaryState() 'ready' (the real list contains `tan`), then Undo (to Composing) → Validate (to Place) → Undo → Redo → Confirm, asserting the stored Session equals current().session after each.
- §2: a failed load shows the banner; after Undo to Composing the primary action is disabled and reads `Word list unavailable` (rule-coverage), then Redo into Place still works, and a reload of session-place.json restores to Place.
- Retry: success and repeat failure; with the retry's route held, the banner is hidden, dictionaryState() is 'loading' and the label is `Loading words…` before the outcome (EXPERIENCE.md State Patterns › Dictionary failed). A 500 failure's Reload refetches in place without reloading the page.
- Timeout: after the route sees the request, page.clock advanced 29 000 ms → still loading, no banner; advanced to 30 000 ms total → banner (build-notes CAP-8). The exact boundary is in the shell Vitest.
- Q-42: after a 404, tapping Reload causes a page load (e.g. `page.waitForEvent('load')`), contrasted with the 500 case. The controlled-service-worker branch is proved in Playwright by P7 in epic 7 (rule-coverage Q-42).
- AD-16: `card-0` and `primary-action` are in the DOM when the held `**/en*.txt` request arrives (rule-coverage AD-16 row). In-load halt: the Q-38 another-window write during boot (e2e/blocking.spec.ts pattern) is halted during boot before mount; the another-window surface shows and, after two rAF round-trips, there are zero `**/en*.txt` requests. After-mount halt: a page started with startHidden waits for card-0 and two in-page rAF round-trips (main.ts parked in whenVisible()), then another window's write halts it while hidden, then showPage; after two rAF round-trips there are zero `**/en*.txt` requests. This does not take over CAP-10's startHidden ordering case (ticket 11).
- Shell Vitest (AD-8): a failure table (500, rejected fetch, a body erroring before abort, '' and '\n' bodies → failed, no unhandled rejection); 404 → failed, then retry() calls a stubbed location.reload(), makes no fetch and state stays 'failed', while after a 500 retry() refetches; first fetch 500, retry() gets a 404 → failed, the next retry() reloads without fetching; a stub body that never enqueues or closes → still loading at 29 999 ms, failed at 30 000 ms fake time, and the same for a retry; a stub body that errors on abort → failed with no unhandled rejection; under a stubbed `navigator.serviceWorker.controller`, Reload after a 404 never calls location.reload(); retry() outside 'failed' and a second load() throw.

## Notes

- Open question: Q-42 under a controlling service worker: after a 404, does Reload still retry in place (banner kept visible) or do nothing? Proposed default: retry in place with the banner kept visible; never reload. Playwright proof is P7 (epic 7).
- Decision: owner, 2026-10-01 (Q-42 under a controlling service worker): after a 404 on the word list, the banner's Reload retries the download in place while the banner stays visible; the page is never reloaded; if the word list loads, Validate works again. Supersedes this ticket's open question.
